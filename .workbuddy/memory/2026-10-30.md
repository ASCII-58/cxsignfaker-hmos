## 签到逻辑链路分析（只读分析，未改代码）

梳理 `SignerPage.ets` + `utils/sign.ets` + `captchaApi/faceApi/upload` 的完整签到编排：

- 链路：initPageData → prepareHint(就绪检查) → handleSignAction(按类型分发) → executeSignFlow(串行逐个用户，间隔 200ms) → signSingleUser → Sign.DoSignInV2 → parseSignResult → recordOutcome(本地 sign_record + LeaderboardReporter 上报) → refreshUserPermissions
- 所有签到类型共用 executeSignFlow 一条路径；二维码签到在 handleSignAction 里先扫码取 enc 再 return。
- 签退走独立 executeSignOutFlow：GetSignInfo → signOutId<=0 记 none → DoSignOut。

### 发现的隐患（待修复 / 待确认）
1. `DoSignOut` 返回值未解析，签退无论成败都 recordOutcome('success')，签退结果不可信。
2. `objectidArr` / `faceObjectIdArr` 与 `signIdArray` 是「下标对齐」而非「userId 映射」；上传后变更勾选会串单人 {\objectId}（prepareHint 只比数量不比对齐）。建议改 `Map<userId, objectId>`。
3. `Sign.lastPreSignEnc` 为静态变量，任一用户的 PreSignIn 都会覆盖；位置签到 GetSignEnc 优先取它，可能拿到他人 enc。
4. AGENTS.md 的能力矩阵把人脸识别只标给二维码/位置签到，但实现上 `openCheckFaceFlag` 与类型正交（faceRequired 对所有类型生效 prepareHint 都拦），文档落后于实现。
5. PreSignIn 内保留大段 LCR007 排查用的 hilog（每段 3000 字符 ×6）与 enc 上下文 dump，每次 loadOtherUsers 对每个用户执行一次，用户多时日志与 checkClassValid 全量课程列表请求开销明显。
